iriaagents

La receta es centrarse en el objetivo.

✓ 20+ proyectos entregados ✓ Skills para Claude Code ✓ Compatible con GitFlow

La idea

Antes de escribir código, responde dos preguntas:

Inmutable · El contrato

¿Qué hay que conseguir?
Y: ¿cómo sabremos que está terminado? El comando exacto con la salida esperada.

Mutable · La orientación

Plan + tareas.
Se espera que evolucione. Refleja lo que aprendes mientras ejecutas.

Esas dos respuestas son el contrato. No cambian.

Todo lo demás — cómo llegar, qué tecnología, en qué orden — se adapta mientras ejecutas. Si la respuesta a la segunda pregunta es vaga, aún no hay un objetivo real.

Regla clave: Sin criterio de verificación ejecutable no existe objetivo válido. El skill no genera archivos hasta que esto esté claro.

/new-task

Una conversación de 7 preguntas. Las dos que más importan:

  • ¿Qué hay que conseguir?
  • ¿Cómo se demuestra que está terminado? — comandos exactos, salida esperada

El skill no avanza si la segunda respuesta es vaga. Una vez acordado, genera tasks/<nombre>/ con todo lo necesario para empezar.

Compatibilidad con GitFlow

Si el proyecto tiene rama develop, el skill crea automáticamente una rama feature/<nombre> y un worktree. El trabajo queda aislado hasta que se consigue el objetivo.

/close-task

El complemento de /new-task. Cierra el ciclo: ejecuta los comandos de verificación del goal.md, captura evidencia, documenta qué cambió respecto al plan original y marca como DONE.

# Dentro del directorio de la tarea:
/close-task

# Ejecuta los comandos de verificación del goal.md
# Captura evidence/close-2026-05-11.md
# Pregunta: ¿qué cambió respecto al plan?
# Marca tasks.md como DONE
El veredicto lo da goal.md, no el plan. Si los tests pasan, la tarea está terminada — independientemente de cuántas veces cambió el plan.

/coach

Lee tus métricas de uso de IA con iria-monitor coach (obsly-ai) y traduce la señal más débil en una acción concreta de iriaagents.

# Requiere: pipx install obsly-ai
/coach

# Ejecuta iria-monitor coach
# Lee coach.json
# Resultado: un problema, una acción
El coach mapea los patrones de tus sesiones al vocabulario iriaagents: sesiones off-track significan goal.md ausente; nada entregado significa /close-task ausente; demasiados cambios de rumbo significan que el criterio de verificación era vago desde el principio.

5 arquetipos

20+ proyectos entregados. Cinco patrones que se repiten:

Corregir N casos fallidos

Tienes una lista de casos incorrectos. El objetivo es llevarlos a cero. Cada caso tiene su spec y la salida esperada.

Tests de conformidad

Suite que captura el sistema de referencia y verifica que la nueva implementación lo replica exactamente.

Migración de legacy

VB6/VFP9/COBOL/PL1 → stack moderno. El test es equivalencia de salida, no revisión de código.

Intérprete / runtime

Implementa soporte de lenguaje. La cobertura se mide en programas que ejecutan correctamente, no en líneas de código.

Nueva funcionalidad

El sistema existe y funciona. Añades algo. El test prueba el nuevo comportamiento observable.

El plan cambia. El objetivo no.

VFP9 Lifecycle — de 0 a 53/53 PASS

El plan inicial era corregir el orden de tres eventos. Durante la ejecución aparecieron ocho problemas nuevos. El plan se reescribió cinco veces. Los tests: ni una coma cambió.

40 bugs cerrados

Las tareas estaban agrupadas por tipo. El orden de ejecución real fue completamente distinto — las dependencias solo se ven cuando ejecutas. El plan lo absorbió. El objetivo nunca se tocó.

Flags --symbols y --tokens

La tarea era solo --symbols. Al implementarlo, apareció la necesidad obvia de --tokens. Se añadió sobre la marcha. El objetivo creció. Los tests crecieron con él.

Reglas de codificación

Cada tarea lleva un coding-rules.md — las restricciones no negociables que el agente debe seguir mientras trabaja. No son preferencias de estilo. Son las reglas que evitan que el agente introduzca patrones que rompan el sistema, conflicten con la arquitectura o generen deuda que nadie pidió.

Qué va en coding-rules.md

CategoríaEjemplos
Lenguaje / frameworkJava 21, sin Lombok, records en lugar de POJOs
Framework de testsSolo JUnit 5 + AssertJ, sin Mockito en el dominio
NomenclaturaLos puertos son interfaces con sufijo Port, los adaptadores con sufijo PersistenceAdapter
Patrones prohibidosSin Map<String,Object> en APIs públicas, sin strings hardcodeados en rutas protegidas
Restricciones de arquitecturaLa capa de aplicación no puede importar de ..persistence..

Por qué importa

Sin reglas de codificación, el agente optimiza para que los tests pasen — lo cual es correcto — pero puede elegir patrones que violan la arquitectura o las convenciones del equipo. Las reglas son la barrera que mantiene la solución dentro de los límites del sistema.

Regla: Si una regla de codificación conflicta con hacer pasar un test, la regla gana. Arregla la regla o arregla el test — no esquives ninguno de los dos en silencio.

Automatizar las reglas

Las mejores reglas de codificación son las que se aplican solas. Si una regla se puede expresar como un linter, un test ArchUnit o una verificación en CI — hazlo. Una regla en un archivo markdown se puede ignorar. Una regla que rompe el build, no.

# Regla: sin Map en APIs públicas → aplicada por ArchUnit
# Regla: sin strings hardcodeados → aplicada por check_frontend_i18n_debt.sh
# Regla: los puertos deben ser interfaces → aplicada por HexagonalArchitectureTest

Arquitectura

Una vez que tienes los tests, la pregunta cambia. Ya no es "¿cómo construimos esto?" — es "¿puede este sistema siquiera hacer esto?"

A veces parte del plan es una pregunta previa: ¿se puede hacer aquí? Un spike de una tarde que responde sí o no. Si sí, los tests ya están escritos — la arquitectura se adapta a las restricciones del sistema. Los tests no dicen cómo implementar. Dicen qué tiene que ocurrir.

Las restricciones se convierten en reglas

Cuando la arquitectura importa, el objetivo no es verificarla una vez — es hacer las filtraciones imposibles. La restricción se convierte en una regla ejecutable que corre en cada cambio. Cero violaciones. Si alguien introduce una filtración, la verificación falla antes de llegar a la revisión.

Arquitectura hexagonal — ArchUnit

Reglas de arquitectura definidas en código, verificadas en cada build. Ningún controlador toca el dominio. Ninguna clase de aplicación bypasea un puerto para acceder directamente a un repositorio. Los puertos son siempre interfaces.

@ArchTest
static final ArchRule aplicacion_no_accede_repositorios_directamente =
    noClasses()
        .that().resideInAnyPackage("com.sfy.wingest.sales.pedcli", ...)
        .and().haveSimpleNameNotEndingWith("PersistenceAdapter")
        .should().dependOnClassesThat()
            .resideInAPackage("com.sfy.wingest.repository..")
        .as("Application must not access JPA repositories directly — use ports");
./mvnw verify
# HexagonalArchitectureTest: pedcli, albcli, prepro, cartera... ✓
# aplicacion_no_accede_repositorios_directamente ✓
# controllers_should_not_access_domain ✓
No es un diagrama. Si alguien introduce un bypass, el build falla.

Glosario como código — Apicurio + Maven JAR

Los términos del dominio viven en Apicurio Registry, exportados como un Maven JAR. El build del backend depende del JAR. Si el glosario es inconsistente, el build falla.

./scripts/ci-export-glossary.sh   # carga el glosario → exporta JAR
./mvnw verify                     # usa el JAR; falla si no existe

i18n como regla

Sin strings hardcodeados en rutas protegidas. Detectado automáticamente en CI — no en revisión de código.

./scripts/check_frontend_i18n_debt.sh
# 0 violations in guarded paths

Tests

El test es el objetivo hecho concreto. No "que funcione" — el comando exacto y la salida exacta que lo demuestra.

Cómo es un buen test

Un test en goal.md tiene tres partes: el comando, la salida esperada o criterio, y nada más.

# Bueno — concreto y ejecutable
bash run-suite.sh
# PASS: 53   FAIL: 0   TOTAL: 53

# Malo — no es un test
"Los eventos del ciclo de vida se disparan en el orden correcto"

Tests por arquetipo

ArquetipoForma del test
Corregir N casos fallidosnode run-spec.js B21.prg → PASS
Conformidadbash run-suite.sh → PASS: N FAIL: 0
Migracióndiff <(legacy in) <(modern in) → sin salida
Intérprete./coverage.sh → 1606/1606 100%
Nueva funcionalidadplaywright test e2e/flow.spec → N passed
Arquitectura./mvnw verify → BUILD SUCCESS, 0 violations

Los tests no cambian. El plan sí.

Una vez que el test está en goal.md queda congelado. Si la implementación toma un camino completamente distinto, el test permanece igual. Si el test necesita cambiar, es una tarea nueva — no una revisión de la actual.

Si el test es vago, el objetivo todavía no existe. El skill no genera archivos hasta que haya un criterio de verificación concreto y ejecutable.

La evidencia debe ser reproducible

Los logs no cuentan. La evidencia tiene que ser verificable a posteriori. En orden de preferencia:

  • ▶
    Traza Playwright o captura de pantalla Para flujos de UI — registra la interacción completa, reproducible en cualquier máquina
  • ⬇
    Dump Export JSON/CSV/SQL del estado final de los datos
  • ±
    Diff de archivos git diff, salida del spec runner — muestra exactamente qué cambió
  • ⬡
    Salida de comando Solo si es la única opción — tests unitarios, verificaciones de arquitectura, lint
  • ✕
    Logs de servidor Efímeros — no demuestran el estado final del sistema

Plantillas

Cada archivo generado por /new-task proviene de una plantilla en templates/. Todos los {{PLACEHOLDERS}} se resuelven durante la generación — ningún placeholder queda sin rellenar.

coding-rules.md

Restricciones no negociables para el agente. Lenguaje, framework de tests, nomenclatura, patrones prohibidos, restricciones de arquitectura. Si una regla conflicta con hacer pasar un test — arregla la regla o arregla el test, no esquives ninguno.

# Reglas de codificación — {{TITLE}}

## 1. No romper nada
Cada cambio debe dejar los tests existentes en verde.

{{SPECIFIC_RULES}}

## Prohibiciones globales
{{GLOBAL_PROHIBITIONS}}

AGENT.md

Instrucciones para el agente. Define el rol, el orden de lectura (goal → plan → coding-rules), el protocolo de ejecución, cuándo parar e informar, y las prohibiciones absolutas.

## Antes de empezar
Lee en orden — sin código hasta haber leído esto:
1. goal.md — problema, estado actual, criterio de éxito
2. plan.md — secuencia de tareas y dependencias
3. coding-rules.md — reglas de estilo

## Prohibiciones
- NO git commit ni git push
- NO marcar como DONE sin ejecutar el criterio verificable
- NO workarounds inventados — parar e informar en su lugar

PROMPT.md

El prompt de lanzamiento — pega en Claude Code o Codex para arrancar el agente. Contiene el rol, el orden de lectura de archivos, el bucle de ejecución y las condiciones de parada.

Eres el agente que {{ROLE_ONE_LINE}}.

Lee estos archivos ANTES de hacer cualquier cambio:
1. tasks/{{NAME}}/goal.md
2. tasks/{{NAME}}/plan.md
3. tasks/{{NAME}}/coding-rules.md

Ejecuta las tareas en orden (task01 → taskNN). Para cada una:
1. Lee taskNN-*.md completo
2. Sigue las instrucciones paso a paso
3. Ejecuta el criterio verificable
4. Solo si pasa, marca como DONE en tasks.md

plan.md y tasks.md

Documentos vivos. Se espera que cambien. plan.md describe el enfoque; reescríbelo cuando la solución real se desvía. tasks.md hace seguimiento del progreso; añade, elimina, reordena según avanza el trabajo. Ninguno es el contrato — goal.md lo es.
