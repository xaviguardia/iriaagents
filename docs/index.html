The recipe is to focus on the objective.

✓ 20+ projects shipped ✓ Claude Code skills ✓ Works with GitFlow

The idea

Before writing code, answer two questions:

Immutable · The contract

What needs to be achieved?
And: how will we know it's done? The exact command with the expected output.

Mutable · The orientation

Plan + tasks.
Expected to evolve. Reflects what you learn while executing.

Those two answers are the contract. They don't change.

Everything else — how to get there, which technology, in what order — adapts as you execute. If the answer to the second question is vague, there's no real objective yet.

Key rule: Without an executable verification criterion, there is no valid objective. The skill won't generate files until this is clear.

/new-task

A conversation of 7 questions. The two that matter most:

  • What needs to be achieved?
  • How do we prove it's done? — exact commands, expected output

The skill won't advance if the second answer is vague. Once agreed, it generates tasks/<name>/ with everything needed to start.

GitFlow support

If the project has a develop branch, the skill automatically creates a feature/<name> branch and worktree. Work stays isolated until the objective is achieved.

/close-task

The complement to /new-task. Closes the loop: runs the verification commands from goal.md, captures evidence, documents what changed from the original plan, and marks DONE.

# Inside a task directory:
/close-task

# Runs goal.md verification commands
# Captures evidence/close-2026-05-11.md
# Asks: what changed from the plan?
# Marks tasks.md as DONE
The verdict comes from goal.md, not the plan. If the tests pass, the task is done — regardless of how many times the plan changed along the way.

5 archetypes

20+ projects shipped. Five patterns that repeat:

Fix N failing cases

You have a list of incorrect cases. The objective is to bring them to zero. Each case has its spec and expected output.

Conformance testing

Suite that captures the reference system and verifies the new implementation replicates it exactly.

Legacy migration

VB6/VFP9/COBOL/PL1 → modern stack. The test is output equivalence, not code review.

Interpreter / runtime

Implement language support. Coverage measured in programs that run correctly, not lines of code.

New functionality

The system exists and works. You add something. The test proves the new observable behaviour.

The plan changes. The objective doesn't.

VFP9 Lifecycle — 0 to 53/53 PASS

The initial plan was to fix the order of three events. While executing, eight previously unseen problems appeared. The plan was rewritten five times. The tests: not a comma changed.

40 bugs closed

The tasks were grouped by type. The actual execution order was completely different — dependencies only become visible when you run things. The plan absorbed it. The objective was never touched.

--symbols and --tokens flags

The task was only --symbols. While implementing it, the obvious need for --tokens appeared. It was added on the fly. The objective grew. The tests grew with it.

When architecture matters

Once you have the tests, the question changes. It's no longer "how do we build this?" — it's "can this system even do this?"

The tests don't say how to implement. They say what has to happen. That leaves room to bend the architecture to real constraints without touching the contract.

Constraints become rules

When architecture, glossary or dependencies matter, the objective isn't to "verify it once" — it's to make leaks impossible. The constraint becomes an executable rule that runs on every change.

Example: newwingest

VFP9/VB6 → Java + React + Python migration. One gate command across three layers:

./scripts/verify.sh
# frontend: lint + build + unit tests
# backend:  Checkstyle + PMD + tests
# iria:     ruff + unit tests
# === All checks passed ===

Example: hexagonal architecture as a test

ArchUnit verifies that no controller touches the domain, that ports are interfaces, and that the application never bypasses a port to hit a repository directly. 20+ rules per module, inside the normal build:

./mvnw verify
# HexagonalArchitectureTest: pedcli, albcli, prepro... ✓
# aplicacion_no_accede_repositorios_directamente ✓
# controllers_should_not_access_domain ✓
It's not a diagram. If someone introduces a bypass, the build fails.

Example: glossary as code

Domain terms live in Apicurio Registry, exported as a Maven JAR. The backend build depends on the JAR. If the glossary isn't consistent, the build fails:

./scripts/ci-export-glossary.sh   # load glossary → export JAR
./mvnw verify                     # uses the JAR; fails if missing

Evidence must be reproducible

Logs don't count. Evidence has to be verifiable after the fact. In order of preference:

  • ▶
    Playwright trace or screenshot For UI flows — records the full interaction, reproducible on any machine
  • ⬇
    Dump JSON/CSV/SQL export of the final data state
  • ±
    File diff git diff, spec runner output — shows exactly what changed
  • ⬡
    Command output Only if it's the only option — unit tests, architecture checks, lint
  • ✕
    Server logs Ephemeral — don't prove the final state of the system

Adding a new skill

Skills are plain Markdown files. Create one, install, done.

vim commands/my-skill.md
./install.sh --force
# available as /my-skill in Claude Code

The skill file describes when to use it, what questions to ask, and what to generate. No code needed.
