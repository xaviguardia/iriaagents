iriaagents

The recipe is to focus on the objective.

✓ 20+ projects shipped ✓ Claude Code skills ✓ Works with GitFlow

The idea

Before writing code, answer two questions:

Immutable · The contract

What needs to be achieved?
And: how will we know it's done? The exact command with the expected output.

Mutable · The orientation

Plan + tasks.
Expected to evolve. Reflects what you learn while executing.

Those two answers are the contract. They don't change.

Everything else — how to get there, which technology, in what order — adapts as you execute. If the answer to the second question is vague, there's no real objective yet.

Key rule: Without an executable verification criterion, there is no valid objective. The skill won't generate files until this is clear.

/new-task

A conversation of 7 questions. The two that matter most:

  • What needs to be achieved?
  • How do we prove it's done? — exact commands, expected output

The skill won't advance if the second answer is vague. Once agreed, it generates tasks/<name>/ with everything needed to start.

GitFlow support

If the project has a develop branch, the skill automatically creates a feature/<name> branch and worktree. Work stays isolated until the objective is achieved.

/close-task

The complement to /new-task. Closes the loop: runs the verification commands from goal.md, captures evidence, documents what changed from the original plan, and marks DONE.

# Inside a task directory:
/close-task

# Runs goal.md verification commands
# Captures evidence/close-2026-05-11.md
# Asks: what changed from the plan?
# Marks tasks.md as DONE
The verdict comes from goal.md, not the plan. If the tests pass, the task is done — regardless of how many times the plan changed along the way.

5 archetypes

20+ projects shipped. Five patterns that repeat:

Fix N failing cases

You have a list of incorrect cases. The objective is to bring them to zero. Each case has its spec and expected output.

Conformance testing

Suite that captures the reference system and verifies the new implementation replicates it exactly.

Legacy migration

VB6/VFP9/COBOL/PL1 → modern stack. The test is output equivalence, not code review.

Interpreter / runtime

Implement language support. Coverage measured in programs that run correctly, not lines of code.

New functionality

The system exists and works. You add something. The test proves the new observable behaviour.

The plan changes. The objective doesn't.

VFP9 Lifecycle — 0 to 53/53 PASS

The initial plan was to fix the order of three events. While executing, eight previously unseen problems appeared. The plan was rewritten five times. The tests: not a comma changed.

40 bugs closed

The tasks were grouped by type. The actual execution order was completely different — dependencies only become visible when you run things. The plan absorbed it. The objective was never touched.

--symbols and --tokens flags

The task was only --symbols. While implementing it, the obvious need for --tokens appeared. It was added on the fly. The objective grew. The tests grew with it.

Coding rules

Every task carries a coding-rules.md — the non-negotiable constraints the agent must follow while working. These aren't style preferences. They're the rules that prevent the agent from introducing patterns that will break the system, conflict with the architecture, or create debt that nobody asked for.

What goes in coding-rules.md

CategoryExamples
Language / frameworkJava 21, no Lombok, records over POJOs
Test frameworkJUnit 5 + AssertJ only, no Mockito on domain
NamingPorts are interfaces suffixed Port, adapters suffixed PersistenceAdapter
Prohibited patternsNo Map<String,Object> in public APIs, no hardcoded strings in guarded paths
Architecture constraintsApplication layer must not import from ..persistence..

Why it matters

Without coding rules, the agent optimises for making the tests pass — which is correct — but may choose patterns that violate the architecture or the team's conventions. The rules are the guard rail that keeps the solution inside the boundaries of the system.

Rule: If a coding rule conflicts with making a test pass, the rule wins. Fix the rule or fix the test — don't silently bypass either.

Automating the rules

The best coding rules are the ones that enforce themselves. If a rule can be expressed as a linter, an ArchUnit test, or a CI check — do it. A rule in a markdown file can be ignored. A rule that breaks the build cannot.

# Rule: no Map in public APIs → enforced by ArchUnit
# Rule: no hardcoded strings → enforced by check_frontend_i18n_debt.sh
# Rule: ports must be interfaces → enforced by HexagonalArchitectureTest

Architecture

Once you have the tests, the question changes. It's no longer "how do we build this?" — it's "can this system even do this?"

Sometimes part of the plan is a prior question: can this be done here? A one-afternoon spike that answers yes or no. If yes, the tests are already written — the architecture adapts to the system's constraints. The tests don't say how to implement. They say what has to happen.

Constraints become rules

When architecture matters, the objective isn't to verify it once — it's to make leaks impossible. The constraint becomes an executable rule that runs on every change. Zero violations. If someone introduces a leak, the check fails before reaching review.

Hexagonal architecture — ArchUnit

Architecture rules defined in code, verified on every build. No controller touches the domain. No application class bypasses a port to reach a repository directly. Ports are always interfaces.

@ArchTest
static final ArchRule aplicacion_no_accede_repositorios_directamente =
    noClasses()
        .that().resideInAnyPackage("com.sfy.wingest.sales.pedcli", ...)
        .and().haveSimpleNameNotEndingWith("PersistenceAdapter")
        .should().dependOnClassesThat()
            .resideInAPackage("com.sfy.wingest.repository..")
        .as("Application must not access JPA repositories directly — use ports");
./mvnw verify
# HexagonalArchitectureTest: pedcli, albcli, prepro, cartera... ✓
# aplicacion_no_accede_repositorios_directamente ✓
# controllers_should_not_access_domain ✓
It's not a diagram. If someone introduces a bypass, the build fails.

Glossary as code — Apicurio + Maven JAR

Domain terms live in Apicurio Registry, exported as a Maven JAR. The backend build depends on the JAR. If the glossary is inconsistent, the build fails.

./scripts/ci-export-glossary.sh   # load glossary → export JAR
./mvnw verify                     # uses the JAR; fails if missing

i18n as a rule

No hardcoded strings in guarded paths. Detected automatically in CI — not in code review.

./scripts/check_frontend_i18n_debt.sh
# 0 violations in guarded paths

Tests

The test is the objective made concrete. Not "it works" — the exact command and the exact output that proves it.

What a good test looks like

A test in goal.md has three parts: the command, the expected output or criterion, and nothing else.

# Good — concrete and executable
bash run-suite.sh
# PASS: 53   FAIL: 0   TOTAL: 53

# Bad — not a test
"The lifecycle events fire in the right order"

Tests by archetype

ArchetypeTest form
Fix N failing casesnode run-spec.js B21.prg → PASS
Conformancebash run-suite.sh → PASS: N FAIL: 0
Migrationdiff <(legacy in) <(modern in) → no output
Interpreter./coverage.sh → 1606/1606 100%
New featureplaywright test e2e/flow.spec → N passed
Architecture./mvnw verify → BUILD SUCCESS, 0 violations

Tests don't change. The plan does.

Once the test is in goal.md it is frozen. If the implementation takes a completely different path, the test stays the same. If the test needs to change, it's a new task — not a revision of the current one.

If the test is vague, the objective doesn't exist yet. The skill won't generate files until there's a concrete, runnable verification criterion.

Evidence must be reproducible

Logs don't count. Evidence has to be verifiable after the fact. In order of preference:

  • ▶
    Playwright trace or screenshot For UI flows — records the full interaction, reproducible on any machine
  • ⬇
    Dump JSON/CSV/SQL export of the final data state
  • ±
    File diff git diff, spec runner output — shows exactly what changed
  • ⬡
    Command output Only if it's the only option — unit tests, architecture checks, lint
  • ✕
    Server logs Ephemeral — don't prove the final state of the system

Adding a new skill

Skills are plain Markdown files. Create one, install, done.

vim commands/my-skill.md
./install.sh --force
# available as /my-skill in Claude Code

The skill file describes when to use it, what questions to ask, and what to generate. No code needed.
