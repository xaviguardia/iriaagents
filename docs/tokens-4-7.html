Claude Opus 4.7: el consumo de tokens casi se duplica respecto a 4.6 — y ahora con datos

No es una sensación. Tras analizar 1.073.725 mensajes de 7.718 sesiones reales de Claude Code en este equipo, los números son tozudos: Opus 4.7 consume casi el doble de tokens por mensaje que Opus 4.6 para el mismo tipo de trabajo. Y la calidad percibida no acompaña.

El problema de fondo: el ecosistema no ofrece herramientas para auditar de dónde sale ese gasto extra. /cost da agregados, pero no desglosa cuántos tokens son razonamiento interno (thinking), cuántos vienen del system prompt de Claude Code, cuántos vienen de los hooks, ni si el tokenizer cuenta distinto en cada versión. El usuario paga, pero no puede auditar.

Hipótesis técnicas que justifican el incremento

Con los datos en la mano, estas son las explicaciones plausibles. Cualquiera de ellas, o varias combinadas, encajan con lo observado:

1. Razonamiento extendido por defecto

Opus 4.7 parece consumir más tokens de thinking internos antes de responder. Si tienes "effortLevel": "high" en tu settings.json, el efecto se multiplica: cada respuesta arrastra una cola de razonamiento invisible pero facturable.

2. System prompt interno más largo

Cada versión de Claude Code embute un prompt de sistema mayor (más reglas, más capacidades, más recordatorios). Eso se cuela en cada turno y no aparece en ningún sitio que el usuario pueda inspeccionar.

3. Más herramientas cargadas por defecto

Plugins LSP, MCP servers, skills, deferred tools… cada herramienta añade schema al contexto inicial. Aunque no la uses, paga sitio en cada llamada.

4. Comportamiento más exhaustivo

4.7 tiende a explorar más antes de actuar: lee más archivos, lanza más sub-agentes, verifica más veces. Pedagógicamente puede estar bien — para la factura no tanto.

5. Context window de 1M activo

Con ventana ampliada, el modelo arrastra más historial entre turnos antes de compactar. Más historial = más tokens leídos en cada respuesta.

Tip Cómo volver a Opus 4.6 desde settings.json

La forma más directa de recuperar el consumo razonable es fijar Opus 4.6 como modelo por defecto. Se hace con una sola línea en el settings.json de Claude Code.

Edición

Abre ~/.claude/settings.json (global) o <proyecto>/.claude/settings.json (por proyecto) y añade: 

{
  "model": "claude-opus-4-6",
  ...resto de tu configuración...
}

Detalles importantes

  • ID exacto: claude-opus-4-6, sin sufijos de fecha.
  • Alcance: el archivo más específico gana (local > proyecto > global).
  • Reinicia Claude Code para que lea el nuevo valor.
  • Verifica con /model: si aparece activo, listo. Si sigue en 4.7, tu plan no incluye 4.6 o el ID está mal escrito.
  • Bonus: con 4.6 puedes usar /fast para acelerar la salida sin degradar a un modelo menor.

Extra: baja también el effortLevel

Si tienes "effortLevel": "high", cámbialo a "medium" o quítalo. Solo este cambio puede reducir el consumo entre un 30% y un 50% sin pérdida apreciable de calidad en tareas normales.

Conclusión

Los datos no mienten: en un corpus de más de un millón de mensajes reales, Opus 4.7 consume ×1,92 tokens por mensaje que Opus 4.6, y en comparativas cabeza a cabeza dentro del mismo día llega a ×4-×5. No estamos diciendo que 4.7 sea un mal modelo — estamos diciendo que cuesta el doble y, en nuestro uso, rinde menos, y que el propio ecosistema no ofrece herramientas para entender de dónde sale ese coste. Hasta que eso cambie, el truco práctico es volver a 4.6 vía settings.json.

Metodología: agregación local de los ~/.claude/projects/**/*.jsonl (sesiones reales de Claude Code de este equipo entre 2026-01-09 y 2026-05-12). Se suma input_tokens + cache_creation_input_tokens + cache_read_input_tokens + output_tokens de cada mensaje del asistente, agrupando por familia de modelo. Cifras: 7.718 archivos, 1.073.725 líneas procesadas, 6 errores de parseo descartados. No es un benchmark formal — es la huella real de uso de un equipo intensivo. Tu mileage puede variar según carga de trabajo, hooks, plugins y MCP servers activos.
